```markdown
# kubectl Reference — Session 6

## Connecting

    az aks get-credentials --resource-group <rg> --name <cluster>
                          Fetch credentials and write them to ~/.kube/config
    kubectl version       Client version, and server version if connected

## Looking at things

    kubectl get all               Everything in the current namespace
    kubectl get pods              Just the pods
    kubectl get pods -o wide      ...with extra columns (IP, node)
    kubectl get pods --show-labels    ...with their labels
    kubectl get deployment        The things managing releases
    kubectl get replicaset        (or 'rs') The things maintaining pod count
    kubectl get service           (or 'svc') The stable network endpoints
    kubectl get events --sort-by=.metadata.creationTimestamp
                                  What the cluster has been doing, oldest first

## Digging deeper

    kubectl describe pod <name>       Full detail on one pod
    kubectl logs <pod-name>           That pod's application output
    kubectl explain <kind>            Built-in docs for any object type
    kubectl get pods -w               WATCH — stream changes live (Ctrl+C to stop)

## Making things happen (imperative — fine for learning)

    kubectl create deployment <name> --image=<image>
    kubectl expose deployment <name> --type=LoadBalancer --port=8080
    kubectl scale deployment <name> --replicas=3
    kubectl set image deployment <name> <container>=<image>:<tag>
    kubectl delete pod <name>

## Making things happen (declarative — what you'd actually use)

    kubectl get deployment <name> -o yaml > deployment.yaml
                                  Generate YAML from what's running
    kubectl apply -f <file>       Make reality match this file
    kubectl diff -f <file>        What WOULD change (like terraform plan)
    kubectl apply -f <file> --dry-run=client    Validate without applying
    kubectl delete -f <file>      Remove what this file describes

## Rollouts

    kubectl rollout status deployment/<name>    Wait until the update completes
    kubectl rollout history deployment/<name>   Previous revisions
    kubectl rollout undo deployment/<name>      Roll back to the previous one
```

### Audience

Trainees who have covered **Docker**, **Session 1 (Azure fundamentals)**, **Session 2 (bash)**, **Session 3 (Jenkins & CI/CD)** and **Sessions 4–5 (Terraform)**.

They are experienced developers: **Node, Express, REST, MVC, SQL, Git, GitHub, Docker, frontend, unit and integration testing**. Four things they already know map directly onto today and should be leaned on hard:

- **MVC** — they already believe in separating concerns. Kubernetes splitting Pod / ReplicaSet / Deployment / Service is the same instinct, and framing it that way saves twenty minutes of confusion
- **REST APIs** — `kubectl` is just an HTTP client. Once that lands, "where does Kubernetes actually live?" answers itself
- **Declarative thinking from Terraform** — `spec` versus `status` is Desired versus Actual, which they met two sessions ago

### 09:00–09:15 — Welcome & Recap: What Docker Didn't Solve

Morning. Let's place today in the story, because Kubernetes makes far more sense as **the answer to a specific problem** than as a thing to learn in the abstract.

You already know **Docker**. You take an application, write a Dockerfile, build an image, and run it anywhere a container runtime exists. In Session 2 you wrote a script that built and pushed an image. In Session 3 you had a pipeline do it automatically.

*REFER TO RESOURCE 1 - SLIDEE* <br>
![intro-to-kubernetes-1](./resources/intro-to-kubernetes-1.png)

Picture a tech team. You're a developer and you want an application deployed. You go to someone in operations. Because of Docker, all they need to ask is "what's your image?" — then run:

*REFER TO RESOURCE 2 - SLIDEE* <br>
```
docker run -p 8080:8080 lfacademy/hello-world-rest-api:0.0.1.RELEASE
```

One command, and it's running. Operations didn't need to know the language, the frameworks, the OS, or any other configuration.

**ASK** <br>
In Session 1 we talked about DevOps breaking down a "wall of confusion" between Dev and Ops. How does that one command demonstrate it? <br>
**ANSWER** <br>
Because the **interface** between the two teams became a single, standard artifact — the image. Dev doesn't have to explain their stack; Ops doesn't have to learn it. All the environment-specific knowledge got packaged into something both sides understand identically. That's the wall coming down in a very literal, practical way — and it's the same idea as an API contract between two services.

**But then reality arrives.** Once that container is running:
- We want the application to **always** be running — what happens when it crashes at 3am?
- We expect **heavier load** at certain times — we want more instances, then fewer
- There are **other applications**, and **new versions** of this one, to deploy — without downtime

**ASK** <br>
Could you solve those three things with Docker alone and a bit of bash? You wrote scripts in Session 2 — what would it take? <br>
**ANSWER** <br>
Sort of, badly. You'd write a script polling whether the container is alive and restarting it. Another starting more containers under load. Another swapping versions over. Now you own a homemade, undocumented, untested orchestration system that only you understand — **and you still have to run it somewhere that itself might fail.** This is precisely the category of problem you don't want to solve yourself, in the same way you don't write your own authentication or your own database.

That's what **Kubernetes** is: a **container orchestration** tool. Docker runs a container; Kubernetes runs *fleets* of containers across *fleets* of machines, and keeps them running.

Today: what Kubernetes is and why, then a real cluster on Azure, then deploying, scaling, self-healing, updating, and finally doing all of it declaratively with YAML you could put in Git.

**Standing rule, and I mean it today: we delete the cluster before we leave.** This is the most expensive thing you've created on this course.

### 09:15–10:00 — Why Kubernetes Exists, and What a Cluster Is

*REFER TO RESOURCE 3 - SLIDEE* <br>
![intro-to-kubernetes-2](./resources/intro-to-kubernetes-2.png)

A **Kubernetes cluster** is a group of servers managed together. Let me show what having one lets you do — **don't type these yet**, just watch what each buys us.

*REFER TO RESOURCE 4 - SLIDEE* <br>
**Deploy an application from an image:**
```
kubectl create deployment hello-world-rest-api --image=lfacademy/hello-world-rest-api:0.0.1.RELEASE
kubectl expose deployment hello-world-rest-api --type=LoadBalancer --port=8080
```

Two commands where Docker took one. Slightly worse so far — but watch.

*REFER TO RESOURCE 5 - SLIDEE* <br>
**Add more instances:**
```
kubectl scale deployment hello-world-rest-api --replicas=3
```

Three instances, with **load balancing between them handled automatically**. You didn't configure a load balancer.

**ASK** <br>
You built a load balancer in Terraform last session. What did that take? <br>
**ANSWER** <br>
**Five resources** — a public IP, the load balancer itself, a backend address pool, a health probe, and a rule — plus a join resource per NIC to put the servers in the pool. That's forty-odd lines of HCL. Kubernetes just did the equivalent from one flag. That's the trade Kubernetes offers: **enormous convenience, in exchange for a whole platform you now have to run and understand.** Worth holding onto that trade all day.

*REFER TO RESOURCE 6 - SLIDEE* <br>
**Keep them running:**
```
kubectl delete pod hello-world-rest-api-<instance-id>
```

Delete an instance and the application keeps working — and within seconds a replacement appears. You always have three.

*REFER TO RESOURCE 7 - SLIDEE* <br>
**Scale automatically under load:**
```
kubectl autoscale deployment hello-world-rest-api --max=10 --cpu-percent=70
```

Up to 10 instances, automatically, when CPU passes 70%.

**ASK** <br>
Where would automatic scaling genuinely matter? <br>
**ANSWER** <br>
Anywhere load is spiky — Amazon on Black Friday, a ticketing site the moment tickets go on sale, a retailer at Christmas. The alternative is provisioning permanently for your **worst hour of the year** and paying for idle capacity the other 8,759 hours.

*REFER TO RESOURCE 8 - SLIDEE* <br>
**Deploy a new version:**
```
kubectl set image deployment hello-world-rest-api hello-world-rest-api=lfacademy/hello-world-rest-api:0.0.2.RELEASE
```

So out of the box, Kubernetes gives us:
- **Auto-scaling** based on load
- **Automatic load balancing** across available instances
- **Monitoring and self-healing** — an instance dies, another starts
- **Zero-downtime releases**

Imagine an old operations team doing this by hand: someone watching dashboards to restart dead services, someone else adding and removing capacity as traffic moves. Kubernetes lets you manage thousands of microservices **declaratively** — you state "there should be 100 instances of this service" and Kubernetes makes it so.

**ASK** <br>
That word "declaratively" — where have you met it in the last two sessions? <br>
**ANSWER** <br>
**Terraform.** You describe the desired end state and the tool reconciles reality to match. Kubernetes is the same idea applied to *running applications* rather than *provisioning infrastructure* — and there's one crucial difference: **Terraform reconciles when you run `apply`. Kubernetes reconciles constantly, forever.** That continuous loop is what makes self-healing possible, and it's the single most important idea today.

**ASK** <br>
Continuous reconciliation between a desired description and actual state. Anything else you use work that way? <br>
**ANSWER** <br>
**React.** You describe what the UI should be for a given state; React diffs that against the DOM and patches the difference, continuously, every time state changes. You never write "remove this div". Kubernetes is that, for containers across machines. If the React model is intuitive to you, **the hardest concept in Kubernetes is already familiar** — you just haven't applied it to servers before.

#### Kubernetes on the cloud

Kubernetes can run anywhere — locally, in a data centre, on any cloud. Setting it up and managing it yourself is genuinely hard, so most teams use a managed engine:

| Provider | Service | Used by |
|---|---|---|
| **Azure** | **Azure Kubernetes Service (AKS)** | Siemens, HP, Heineken |
| **AWS** | Amazon Elastic Kubernetes Service (EKS) | Netflix, GoDaddy |
| **GCP** | Google Kubernetes Engine (GKE) | YouTube, Google Maps, Google Search |

We'll use **AKS**.

#### What's actually in a cluster?

Kubernetes is, at heart, a **resource manager**.

**ASK** <br>
What resources does it manage? <br>
**ANSWER** <br>
Servers. Virtual servers in the cloud.

Every provider has a different name for a generic virtual server:
- **Azure**: Virtual Machines
- **AWS**: EC2 instances
- **GCP**: Compute Engine

**Kubernetes calls them `nodes`.**

*REFER TO RESOURCE 9 - SLIDEE* <br>
![intro-to-kubernetes-3](./resources/intro-to-kubernetes-3.png)

Kubernetes can manage thousands of nodes. To oversee that many it introduces managers — historically **Master Nodes**, today almost always the **control plane**.

So a **cluster** is a combination of nodes:
- **Worker nodes** (usually just "nodes") — the ones that actually run your applications
- **Control plane** — oversees the workers: are they available, are they doing work, is the desired state being met

**NOTE FOR TRAINERS** <br>
Worth calling out as a genuine AKS advantage: Azure **fully manages and hosts the control plane at no extra cost**. You don't see it, configure it, or pay for it as a resource — you only see and pay for the **worker nodes** in your **node pool**. That differs from providers where you choose a zonal versus regional control plane or pay a per-cluster management fee. With AKS there is simply nothing to configure there. <br>
**END OF NOTE**

**ASK** <br>
Given the control plane continuously checks whether reality matches desired state — what does that remind you of from Terraform? <br>
**ANSWER** <br>
The **three states**. The control plane holds the **desired state** ("3 replicas of this image"), observes the **actual state** ("only 2 pods running"), and continuously reconciles. The difference is that Terraform does it when *you* run a command; the Kubernetes control plane does it in a permanent loop. It's genuinely called the **reconciliation loop**, and everything else today follows from it.

#### While it's building — a few facts

- You'll see Kubernetes abbreviated **K8s** — `K`, then *eight letters*, then `s`. Same pattern gives you `i18n` for internationalisation and `a11y` for accessibility
- The logo is a ship's helm — the name comes from the Greek for *helmsman* or *pilot*. The whole vocabulary is nautical: containers, pods, helm charts. It's one extended metaphor about steering cargo
- The managed offerings again: **AKS** (Azure), **EKS** (AWS), **GKE** (GCP)

**ASK** *(good filler while waiting)* <br>
Kubernetes is genuinely complex. When is it **the wrong choice**? <br>
**ANSWER** <br>
More often than people admit. If you have **one small application with steady traffic**, a single VM running Docker — exactly what you built in Terraform last session — is simpler, cheaper, and has far less to go wrong. Azure App Service or Container Apps would be simpler still. Kubernetes earns its complexity when you have **many services**, **variable load**, **a team large enough that self-service matters**, or **a genuine need for zero-downtime releases and self-healing**. "We use Kubernetes because it's what people use" is how teams end up maintaining a platform more complex than the application running on it. Being able to say *when not to* is a senior instinct.

#### Touring the cluster

Once it's ready:

*(In the Azure Portal — Kubernetes services → your cluster)*

The top-level list shows the cluster's **name**, **location**, **Kubernetes version** and **number of nodes**.

Click into the cluster. On the left-hand panel:
- **Node pools** — where your worker nodes live
- **Workloads** — the applications running in the cluster
- **Secrets** — secure storage for values tied to the cluster
- **Services and ingresses** — how traffic reaches your applications

**Overview** shows:
- **Kubernetes version**
- **API server address** — how tools like `kubectl` reach the control plane
- **Region**

**NOTE FOR TRAINERS** <br>
Unlike GKE, which shows a "control plane zone" alongside "default node zones", AKS **doesn't expose control-plane location at all**. That's Azure's infrastructure to manage, not ours to inspect. Everything visible and configurable relates to **nodes**. <br>
**END OF NOTE**

*(In the Azure Portal — your cluster → Node pools)*

Click into the node pool, then into an individual node:

- **CPU requested** — measured in **mCPU**, "milliCPU". `1000 mCPU` is one whole CPU core, so `250 mCPU` is a quarter of a core. A **Kubernetes-level** unit, identical on every cloud
- **CPU allocatable** — how much is available for your applications
- **Memory available** — likewise

**ASK** <br>
You chose a VM size with, say, 2 vCPUs and 7 GiB. Look at what's actually **allocatable** — it's less. Where did the rest go? <br>
**ANSWER** <br>
**Kubernetes itself.** Every node runs agent processes — the kubelet, the container runtime, networking components — and the OS needs headroom. That overhead is reserved before your applications get anything. It's a real planning consideration: **a cluster of many tiny nodes wastes proportionally far more on overhead than a cluster of fewer larger ones.** Same reason you don't run twenty microservices each in their own 256MB container if five would do.

**Step 3** — the Kubernetes version will be whatever AKS currently defaults to (e.g. `1.30.x`). The API server address is a hostname ending **`.azmk8s.io`**. That hostname is what `kubectl` talks to — worth flagging now, because it makes the 11:15 point about kubectl-as-API-client concrete.

**Step 4** — the default node pool VM size is typically `Standard_DS2_v2` (2 vCPU, 7 GiB) or similar.

**Step 5** — expect roughly **10–25%** of CPU and memory reserved, **proportionally more on smaller nodes**. The takeaway: **you never get 100% of what you pay for.**

**Step 7 — the pricing answer, which matters for the teardown:**

| Part | Chargeable? |
|---|---|
| **Control plane** | **Free** on the standard AKS tier |
| **Worker node VMs** | **Yes** — standard VM pricing, per node, per hour |
| **Managed disks** for the nodes | **Yes** |
| **Load balancer** created by a `LoadBalancer` Service | **Yes** |
| **Public IP** attached to it | **Yes** |
| Outbound data transfer | Yes, beyond the free allowance |

So "the control plane is free" is true and slightly misleading — **everything you can actually see costs money**, and it accrues per hour whether you use it or not. That's the argument for the 16:45 teardown, made with numbers rather than nagging.

**If a cluster fails to create**, the usual causes are **insufficient quota** for that VM family in that region (try a different region or a smaller VM size) or **insufficient credit**.

### 12:15–13:00 — Pods and ReplicaSets
*(Activity: 20 min + challenge)*

Getting an application running was the easy part. Understanding what happened is where the learning is.

*(Run in Cloud Shell)*
```bash
kubectl get events
```

A lot comes back, all relating to what the cluster has been doing.

![intro-to-kubernetes-14](./resources/intro-to-kubernetes-14.png)

You can see a **pod** created, an image pulled, and a sequence of steps starting a container. There's also a **replica set**, a **deployment**, and a **service**.

We created *one deployment* and *exposed it*. Kubernetes made **four things**. Why?

#### The Single Responsibility Principle

Kubernetes deliberately follows the **Single Responsibility Principle**: **one concept, one responsibility.** Rather than one big "running application" object, it splits the job:

| Object | Its one job |
|---|---|
| **Pod** | Run containers |
| **ReplicaSet** | Ensure a specific number of Pods exist |
| **Deployment** | Manage releases and version changes without downtime |
| **Service** | Provide a stable network endpoint |

`kubectl create deployment` made the **Pod, ReplicaSet and Deployment**. `kubectl expose deployment` made the **Service**.

**ASK** <br>
Why split it? Why not one object doing all four jobs? <br>
**ANSWER** <br>
**You already know the answer — it's MVC.** You don't put your database queries in your route handlers, because the four jobs change independently and at different rates. Same here: you change *how many instances you want* far more often than *which version is deployed*. You change the version far more often than the *network endpoint* — and you specifically **don't want** the endpoint to change when the others do. Separating them means each can be reasoned about, changed and replaced without touching the others. It's the exact argument for splitting a monolith into modules, applied to the runtime.

Let's look at each.

*(Run in Cloud Shell)*
```bash
kubectl get pods
kubectl get replicaset
kubectl get deployment
kubectl get service
```

Look at the **Pod name**: `hello-world-rest-api-5b78b5c566-m8jh4`. Three parts:
- `hello-world-rest-api` — the **Deployment** name
- `5b78b5c566` — the **ReplicaSet** ID
- `m8jh4` — this **Pod's** own ID

**The naming literally encodes the hierarchy**: a Deployment owns a ReplicaSet, which owns Pods. Remember that when reading output later — it tells you at a glance which Pods belong together.

#### Pods

*REFER TO RESOURCE 13 - SLIDEE* <br>
![intro-to-kubernetes-21](./resources/intro-to-kubernetes-21.png)

A **Pod** is the **smallest deployable unit** in Kubernetes. **You cannot create a bare container** — every container lives inside a Pod.

*(Run in Cloud Shell)*
```bash
kubectl get pods -o wide
```

![intro-to-kubernetes-22](./resources/intro-to-kubernetes-22.png)

`-o wide` means "output wide" — more columns. Two matter:
- **IP** — each Pod gets its own IP, unique within the cluster
- **READY** — showing `1/1`: how many containers in the Pod are ready, out of how many exist

**A Pod can hold multiple containers.** They share the Pod's resources, share its IP, and can talk to each other over **`localhost`**.

**ASK** <br>
When would you deliberately put two containers in one Pod, rather than two separate Pods? <br>
**ANSWER** <br>
When they're genuinely **inseparable** — one is a helper for the other and they must live and die together on the same machine. The classic example is a **sidecar**: your application container plus a log-shipping container reading the app's log files, or a proxy handling TLS. <br>
**The test:** *"would it ever make sense to have three of one and five of the other?"* If yes, separate Pods. It's the same question as deciding whether two things belong in the same `docker compose` service or two.

*(Run in Cloud Shell)*
```bash
kubectl explain pods
```

*"A collection of containers that can run on a host."* "Host" means a **node**. So:

**A node can hold many Pods. A Pod can hold many containers.**

*(Run in Cloud Shell)*
```bash
kubectl get pods
kubectl describe pod <paste-the-full-pod-name>
```

![intro-to-kubernetes-24](./resources/intro-to-kubernetes-24.png)

`describe` gives far more than `get`. Notable fields:

- **Name** and **IP**
- **Node** — which server it's running on
- **Namespace** — `default`. **Namespaces provide isolation within a cluster.** You could run Dev and QA in the same cluster, separated by namespace
- **Labels** — here `app=hello-world-rest-api`. **This is how Pods, ReplicaSets and Services find each other** — via labels and *selectors*, not by name or IP
- **Annotations** — metadata: author, build ID
- **Status** — is it running

**ASK** <br>
Labels are just arbitrary key/value strings. Why is that a better way to connect a Service to its Pods than listing Pod names or IPs? <br>
**ANSWER** <br>
Because **Pods are disposable** — names and IPs change constantly. A Service saying "send traffic to Pod `m8jh4`" would break the moment that Pod was replaced. Instead it says "send traffic to anything labelled `app=hello-world-rest-api`", and whatever currently matches gets the traffic. **It's a query, evaluated continuously, not a fixed list.** <br>
You already use this pattern: it's a **CSS selector**. You don't style `#element-4f3a`; you style `.button`, and whatever currently has that class gets the styling — including elements that didn't exist when you wrote the rule.

#### ReplicaSets

*(Run in Cloud Shell)*
```bash
kubectl get replicaset       # or the shorthand: kubectl get rs
```

A ReplicaSet's job: **ensure a specific number of Pods are running at all times.** Columns:
- **DESIRED** — how many we asked for
- **CURRENT** — how many exist
- **READY** — how many have containers actually ready to serve

Let's test the self-healing claim.

*(Run in Cloud Shell)*
```bash
kubectl get pods -o wide
```

Copy the full Pod name, then delete it:

*(Run in Cloud Shell)*
```bash
kubectl delete pod hello-world-rest-api-5b78b5c566-m8jh4
kubectl get pods -o wide
```

![intro-to-kubernetes-27](./resources/intro-to-kubernetes-27.png)

The old Pod is gone — and a **new one has appeared**. Note the name: the middle section (`5b78b5c566`) is **identical**, because it belongs to the same ReplicaSet; only the final ID differs.

And the URL still works.

**That's the reconciliation loop.** The ReplicaSet continuously compares desired (1) against actual, and the moment actual dropped to 0 it created a replacement. **Nobody was watching a dashboard.**

#### Scaling

*(Run in Cloud Shell)*
```bash
kubectl scale deployment hello-world-rest-api --replicas=3
kubectl get pods
```

![intro-to-kubernetes-29](./resources/intro-to-kubernetes-29.png)

Three Pods — and note the **AGE** column: one is older than the other two. **You didn't say "add two more".** You said "there should be three", and Kubernetes worked out the difference.

**ASK** <br>
Where have you seen that exact behaviour? <br>
**ANSWER** <br>
**Terraform**, two sessions ago — setting `count = 3` when 2 existed created exactly one. Same declarative principle: **you state the total, not the delta.**

*(Run in Cloud Shell)*
```bash
kubectl get replicaset
kubectl get events --sort-by=.metadata.creationTimestamp
```

`--sort-by` orders by a field path — here creation timestamp, so newest are at the bottom. Without it events come back unsorted, which is nearly unreadable.

Near the bottom you'll see the scale-up, then image pulls, then containers starting.

### 14:00–14:45 — Deployments and Zero-Downtime Releases
*(Activity: 10 min)*

We've covered Pods and ReplicaSets. So why do we need a **Deployment** on top?

Picture version 1 running, and you want version 2 live. The requirement is **zero downtime** — users keep using the app throughout.

*(Run in Cloud Shell)*


- Syntax: `kubectl set image deployment <deployment-name> <container-name>=<image>:<tag>`

#### Deliberately breaking it first

Let's do something interesting: deploy a **deliberately broken image** and watch what happens.

*(Run in Cloud Shell)*
```bash
kubectl set image deployment hello-world-rest-api hello-world-rest-api=DUMMY_IMAGE:test
```

Reading the command:
- `hello-world-rest-api` (first) — the **Deployment** name
- `hello-world-rest-api` (second) — the **container** name inside the Pod. They happen to match here, which confuses people
- `DUMMY_IMAGE:test` — an image path that doesn't exist

Kubernetes reports the image was updated. **That's concerning** — we know it's fake.

*(In your browser)* — refresh the application endpoint.

**It still works.** The old version is serving traffic perfectly.

*(Run in Cloud Shell)*
```bash
kubectl get rs -o wide
kubectl get pods
```

![intro-to-kubernetes-34](./resources/intro-to-kubernetes-34.png)

**Two ReplicaSets now:**
1. The original — real image, 3 Pods, older
2. A new one — the DUMMY image, **1 desired, 0 ready**

The new Pod has status **`InvalidImageName`** (or `ErrImagePull` / `ImagePullBackOff` for a well-formed but non-existent image).

*(Run in Cloud Shell)*
```bash
kubectl describe pod <the-broken-pod-name>
kubectl get events --sort-by=.metadata.creationTimestamp
```

The sequence in the events:
- A new **Deployment** rollout started
- The Deployment created a new **ReplicaSet**
- That ReplicaSet asked for **one** Pod
- The Pod **failed to start**
- ...and everything stopped there

*REFER TO RESOURCE 12 - SLIDEE* <br>
![intro-to-kubernetes-37](./resources/intro-to-kubernetes-37.png)

**ASK** <br>
This is the single most valuable thing in today's session. Why did a completely broken deployment cause **zero** user impact? <br>
**ANSWER** <br>
Because the Deployment creates the new version **alongside** the old one and only scales the old one down **as the new one proves healthy**. The new Pod never became Ready, so the old ReplicaSet was never scaled down — all three original Pods kept serving. **The rollout simply stalled.** <br>
Compare that with `terraform apply` failing halfway in Session 5: you're left in a broken, half-applied state with no automatic rollback. A Kubernetes Deployment **refuses to take down working capacity for something that isn't working yet.**

**ASK** <br>
And compare it to your Jenkins pipeline from Session 3. Same instinct? <br>
**ANSWER** <br>
**Exactly the same** — "don't let the broken thing reach users" — but enforced at a different layer. Jenkins gates at **build time**: tests fail, nothing gets pushed. Kubernetes gates at **runtime**: the new Pod never becomes healthy, so it never receives traffic. **Two independent safety nets at two different points**, and you want both, because they catch different failures. A pipeline can't catch a container that starts fine in CI and crashes on the cluster.

#### Now a real release

*(Run in Cloud Shell)*
```bash
kubectl set image deployment hello-world-rest-api hello-world-rest-api=lfacademy/hello-world-rest-api:0.0.2.RELEASE
kubectl get pods
```

If you were quick, you'd have seen the three original Pods with status **`Terminating`** while new ones started. Run `kubectl get pods -w` **before** the `set image` next time and you can watch the whole handover live. <br>
**END OF NOTE**

*(Run in Cloud Shell)*
```bash
kubectl get rs
```

**Three ReplicaSets:**
1. The original v1 — now scaled to 0
2. The broken DUMMY one — 0
3. The new v2 — 3 Pods running

*(In your browser)* — refresh. You're on **v2**.

*(Run in Cloud Shell)*
```bash
kubectl get events --sort-by=.metadata.creationTimestamp
```

The rollout sequence, step by step:
- Deployment creates a new ReplicaSet for **v2**
- Gives it **one** Pod
- That Pod runs a v2 container and becomes Ready
- Scales **v1 down** to 2
- Scales **v2 up** to 2
- Scales **v1 down** to 1
- Scales **v2 up** to 3
- Scales **v1 down** to 0

**It updates one Pod at a time**, always keeping enough healthy capacity serving. That's a **rolling update**, the default strategy.

**ASK** <br>
Those old ReplicaSets are sitting there at 0 replicas. Why keep them rather than delete them? <br>
**ANSWER** <br>
**Rollback.** The old ReplicaSet still knows exactly which image and configuration it ran. If v2 turns out to be broken in a way that only shows under real traffic, `kubectl rollout undo` scales the previous ReplicaSet back up and the current one down — **in seconds, with no rebuild and no pipeline run**. Keeping the history is what makes instant rollback possible. It's `git revert` for running infrastructure. (`revisionHistoryLimit` controls how many are kept; you'll see it in the YAML later.)

Worth showing:

*(Run in Cloud Shell)*
```bash
kubectl rollout history deployment hello-world-rest-api
kubectl rollout status deployment hello-world-rest-api
```

#### Summary of the four concepts

*REFER TO RESOURCE 13 - SLIDEE* <br>
![intro-to-kubernetes-40](./resources/intro-to-kubernetes-40.png)

**Pods** — wrappers for a set of containers. Have an IP, labels and annotations.

**ReplicaSets** — ensure a specific number of Pods run. In practice each is tied to **one release version**.

**Deployments** — manage release upgrades without downtime. Strategies:
- **Rolling update** (default) — replace Pods gradually, as we just saw
- **Blue/green** — stand up the full new version, then switch traffic across at once
- **Canary** — send a small percentage of traffic to the new version first

Kubernetes has real depth beyond this, but these four carry most of the day-to-day work.

### 14:45–15:00 — Services, Regions and Availability Zones
*(Research activity: 15 min)*

#### Why Services exist

*(Run in Cloud Shell)*
```bash
kubectl get pods -o wide
```

**NOTE FOR TRAINER**: *DON'T CLEAR THE TERMINAL* — you want the old IPs visible for comparison.

Each Pod has its own IP. But the endpoint you've been visiting matches **none of them** — traffic is being distributed across all three.

Now delete a Pod:

*(Run in Cloud Shell)*
```bash
kubectl delete pod <pod-name>
kubectl get pods -o wide
```

**ASK** <br>
Compare against the earlier output. What's different? <br>
**ANSWER** <br>
The replacement Pod has a **new IP address**. Every Pod gets a fresh IP when it starts.

That's a problem. If users connected directly to Pod IPs, **every self-heal, every scale event and every release would break their connection.** We need one endpoint that never changes.

**As far as Kubernetes is concerned, a Pod is a throwaway resource.** They're built expecting to be destroyed and recreated. The job of a **Service** is to provide an **always-available interface** to whatever Pods currently exist — a permanent address in front of impermanent things.

**ASK** <br>
A stable name in front of things whose addresses keep changing. What else in your daily work does that? <br>
**ANSWER** <br>
**DNS** — you connect to `api.example.com`, not to whatever IP it resolves to today. Also a **load balancer** in front of an autoscaling group, and arguably an **interface** in front of implementations. Same pattern everywhere: **a stable identifier decoupled from a changing implementation**, so consumers don't have to care.

To recap what created what:
- `kubectl create deployment <name> --image=<image>` → Pods, ReplicaSet, Deployment
- `kubectl expose deployment <name> --type=<type> --port=<port>` → Service

*(In the Azure Portal — your cluster → Services and ingresses → your service)* — you can see the labels, the associated deployment, the external IP, and the Pods currently serving requests.

*(In the Azure Portal — search **Load balancers**)*

There's a **real Azure Standard Load Balancer**, created automatically, in the same resource group as your node pool.

**ASK** <br>
In Session 5 you built a load balancer by hand: public IP, LB, backend pool, health probe, rule. Here one `kubectl expose` did all of it. Is that strictly better? <br>
**ANSWER** <br>
It's faster and far less error-prone for the common case — **but you've given up fine-grained control, and it's now implicit.** Nothing in your Git repository says "there is an Azure load balancer". Someone reading your Terraform knows exactly what exists; someone reading a `kubectl expose` command has to *know* that Kubernetes provisions cloud resources on their behalf. <br>
That's the trade every abstraction makes — the same trade as an ORM versus hand-written SQL. And it has a concrete consequence for us today: **deleting the Service is what deletes the load balancer.** You can't manage it in the Portal, and if you forget it, it survives and keeps charging you.

#### Service types

*(Run in Cloud Shell)*
```bash
kubectl get services
```

Two services: our **LoadBalancer**, and **`kubernetes`**, which is a **ClusterIP**.

- **ClusterIP** — reachable **only from inside the cluster**. Note it has **no EXTERNAL-IP**. Used for internal service-to-service communication — your API talking to a database
- **LoadBalancer** — asks the cloud provider for a public load balancer and external IP. What we used
- **NodePort** — opens a specific port on every node; reachable from outside via any node's IP. A middle ground, more common outside managed clouds

#### Regions and availability zones

We chose a region when creating the cluster. Worth a moment on why — though most of this is Session 1 revision.

*(In your browser)* — search **Azure global infrastructure**:
https://azure.microsoft.com/en-us/explore/global-infrastructure/geographies/

Azure runs **60+ regions**, grouped into **geographies** to help meet data-residency requirements.

**ASK** <br>
What is **latency**, and what is **availability**? <br>
**ANSWER** <br>
**Latency** — the time for requests and responses to traverse a network. If all your users are in Wolverhampton but you deploy to Melbourne, every request makes a round trip across the world. **Availability** — the ability to reach your resources at all. If there were flooding in London, users shouldn't lose the application entirely.

Within a region there are **Availability Zones** — physically isolated locations with independent power and networking. Azure uses the same term as AWS (GCP just says "zones"). Most Azure regions supporting AZs have **3**.

**NOTE FOR TRAINERS** <br>
One difference worth flagging versus GCP: **not every Azure region supports Availability Zones at all.** GCP regions uniformly have zones; Azure's don't. Always check the regions page for whichever region you're planning to use — this catches people out when designing for resilience. <br>
**END OF NOTE**

**HANDS ON — research (15 min)** <br>
**In pairs**, produce short written answers:

1. **Service types.** For each of `ClusterIP`, `NodePort` and `LoadBalancer`, write one sentence on **when you'd choose it**. Then: if you had ten applications to expose, what's wrong with ten `LoadBalancer` Services?
2. **Ingress.** Look up **Kubernetes Ingress**. In two sentences, what problem does it solve that a `LoadBalancer` Service doesn't?
3. **Probes.** Look up **liveness** and **readiness probes**. What's the difference, and which one prevented downtime during our rolling update?
4. **Cost check.** Go to **Load balancers** in the Portal and find the one Kubernetes created for you. Which resource group is it in, and what happens to it if you delete the whole cluster but forget the Service first?
5. **(Stretch)** Read about **`kubectl` contexts**. If you managed a dev cluster and a prod cluster, how would you avoid running a command against the wrong one?

**Solution**

**1 — Service types:**

| Type | When |
|---|---|
| **ClusterIP** | Internal-only traffic — your API talking to a cache or database. **The default, and the right one most of the time** |
| **NodePort** | Rare in managed clouds. Useful on bare metal or locally, where no cloud load balancer exists |
| **LoadBalancer** | You need a public entry point and you're on a cloud that can provide one |

**The problem with ten `LoadBalancer` Services:** each one provisions **its own Azure load balancer and its own public IP**, all chargeable. Ten applications means ten public IPs, ten sets of billing, and ten DNS records to manage. That's what Ingress fixes.

**2 — Ingress.** An **Ingress** is a single entry point that routes to multiple Services based on **hostname or URL path** — `/api` to one Service, `/admin` to another, all behind **one** load balancer and **one** IP. It's a reverse proxy managed by Kubernetes. Think of it as Express routing, but for the whole cluster rather than one app.

**3 — Probes.**
- A **readiness probe** tells Kubernetes whether a Pod is ready to **receive traffic**
- A **liveness probe** tells it whether a Pod is still alive or needs **restarting**

Without a readiness probe, Kubernetes considers a Pod ready as soon as the container **process starts** — which for most applications is *before* it can actually serve requests. During a rolling update that means scaling down the old version while the new one is still warming up, causing exactly the downtime the Deployment is meant to prevent. **It's the same job as the `azurerm_lb_probe` you configured in Terraform**, but evaluated continuously by the cluster.

**4 — Cost check.** The load balancer lives in the **auto-generated `MC_...` resource group**, not the one you created. If you delete the cluster but the Service was never deleted, that load balancer and its public IP **can survive** — which is exactly why the teardown sequence deletes the Service first.

**5 — Contexts.** `kubectl config get-contexts` lists them, `kubectl config current-context` shows which you're on, and `kubectl config use-context <name>` switches. The genuine answer to "how do I avoid running a command against prod": **make the current context visible in your shell prompt** — tools like `kubectx`/`kube-ps1` do this — so you can't forget. Every experienced Kubernetes engineer has a prod horror story that starts with "I thought I was on dev".

**ASK** <br>
`spec` is desired state, `status` is actual state maintained by the cluster. What does that map onto from Sessions 4 and 5? <br>

- **deployment.yaml → `spec.template.spec.containers[].image`** — the image being run
- **deployment.yaml → `status.availableReplicas`** — currently 3
- **service.yaml → `spec.type`** — `LoadBalancer`

Note `spec.template` — that's a **Pod template**. The Deployment's spec *contains a description of the Pods to create*. **That nesting is the Deployment → ReplicaSet → Pod hierarchy, expressed in one file.**

#### Part A3 (≈10 min) — Apply a change from YAML

Let's change the replica count declaratively rather than with `kubectl scale`.

**deployment.yaml**
```yaml
spec:
  progressDeadlineSeconds: 600
  # UPDATED
  replicas: 2
  revisionHistoryLimit: 10
  selector:
    matchLabels:
      app: hello-world-rest-api
```

Save, then:

*(Run from `~/k8s-training/starter-code/kubernetes/01-hello-world-rest-api`)*
```bash
kubectl apply -f deployment.yaml
kubectl get pods
```

Two Pods.

**`kubectl apply -f <file>`** is the declarative command:
- `apply` — "make reality match this file". Creates what's missing, updates what differs, leaves what matches alone
- `-f` — the file to read

**ASK** <br>
What's the practical difference between `kubectl apply -f deployment.yaml` and `kubectl scale deployment ... --replicas=2`? <br>
**ANSWER** <br>
The end state is identical — but **only one of them leaves a record.** The YAML can be committed, diffed, reviewed in a pull request, and re-applied to a different cluster to produce the same result. The `scale` command exists only in your shell history. <br>
And `apply` is **idempotent**: run it ten times and nothing changes after the first. That word should be familiar from Session 2 and again from Terraform — it's the property that makes something **safe to run in a pipeline**, where you can't guarantee it won't run twice.

**NOTE FOR TRAINER** <br>
You'll hit errors applying further changes without cleaning up the generated file. `kubectl get -o yaml` dumps **everything**, including runtime-only fields (`status`, `metadata.uid`, `resourceVersion`, `creationTimestamp`, `managedFields`) that Kubernetes rejects or ignores on apply. That's the point of Part B — **don't skip it**, and warn students before they start experimenting. <br>
**END OF NOTE**

#### Part B (≈50 min) — Clean the YAML into something you'd commit

Generated YAML is a **starting point**, not a finished artifact. A file you'd actually put in Git contains only what **you** are asserting, not what the cluster reported back.

**ASK** *(before they start)* <br>
Why does it matter that a committed manifest contains only your assertions? <br>
**ANSWER** <br>
Because a file mixing **intent** with **observed runtime facts** is unreviewable. A reviewer can't tell which lines are decisions and which are noise, the diff churns every time you regenerate it, and fields like `resourceVersion` are meaningless — or actively wrong — on a different cluster. **It's the difference between a schema migration and a database dump.** One expresses intent; the other is a snapshot.

**Your task:** produce a `deployment.yaml` and a `service.yaml` that are:
- Free of runtime-generated fields
- Applicable repeatedly with no errors
- **Readable** — someone could review them in a pull request and understand what they do

**Delete from both files:**
- The entire `status:` block at the bottom
- Inside `metadata`: `uid`, `resourceVersion`, `generation`, `creationTimestamp`, `selfLink`, `managedFields`, and the `annotations` block containing `deployment.kubernetes.io/revision` and `kubectl.kubernetes.io/last-applied-configuration`
- In `service.yaml`: `spec.clusterIP`, `spec.clusterIPs`, and anything under `status.loadBalancer`

**Then test properly:**

*(Run from `~/k8s-training/starter-code/kubernetes/01-hello-world-rest-api`)*
```bash

kubectl apply -f service.yaml
kubectl apply -f deployment.yaml    # run it AGAIN — should be clean, "unchanged"
```

**Then prove they're real infrastructure-as-code:**
1. Change `replicas` to `4` in the file, apply, confirm with `kubectl get pods`
2. Change the image tag to `0.0.1.RELEASE`, apply, and watch the rolling update with `kubectl get pods -w`
3. **Delete the deployment entirely** (`kubectl delete deployment hello-world-rest-api`), then **recreate it from your file alone**

**Solution**

A cleaned `deployment.yaml` — everything below is something you're **asserting**, nothing is reported state:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-world-rest-api
  labels:
    app: hello-world-rest-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hello-world-rest-api
  template:
    metadata:
      labels:
        app: hello-world-rest-api
    spec:
      containers:
        - name: hello-world-rest-api
          image: lfacademy/hello-world-rest-api:0.0.2.RELEASE
          ports:
            - containerPort: 8080
```

A cleaned `service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: hello-world-rest-api
  labels:
    app: hello-world-rest-api
spec:
  type: LoadBalancer
  selector:
    app: hello-world-rest-api
  ports:
    - port: 8080
      targetPort: 8080
      protocol: TCP
```

Reading the important parts:

- **`spec.selector.matchLabels`** (Deployment) — "the Pods I manage are the ones with this label"
- **`spec.template.metadata.labels`** — "the Pods I create get this label". **These two must match**, or the Deployment creates Pods it doesn't consider its own. **It's the single most common YAML mistake there is**
- **`spec.selector`** (Service) — "send traffic to Pods with this label". Same label again — that's the entire link between Service and Pods, and it's the CSS-selector idea from this morning made explicit
- **`port` vs `targetPort`** — `port` is what the Service listens on; `targetPort` is the port on the container. Often the same, don't have to be

The full test sequence:

*(Run from `~/k8s-training/starter-code/kubernetes/01-hello-world-rest-api`)*
```bash
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml

# Idempotency — the second run should report "unchanged"
kubectl apply -f deployment.yaml

# 1. Scale declaratively: edit replicas to 4, then
kubectl apply -f deployment.yaml
kubectl get pods

# 2. Roll back a version: edit image tag to 0.0.1.RELEASE, then
kubectl apply -f deployment.yaml
kubectl get pods -w              # watch the rolling update live, Ctrl+C to stop
kubectl get rs -o wide           # see the ReplicaSets swap over

# 3. Delete and recreate from the file alone
kubectl delete deployment hello-world-rest-api
kubectl get pods                 # all gone
kubectl apply -f deployment.yaml
kubectl get pods                 # back, from the file
```

**Step 3 is the payoff of the entire day.** Your application definition is now **a text file**. Delete everything, apply the file, and it comes back identically. That file can be reviewed in a pull request, applied to a different cluster, or run by a Jenkins pipeline.

**ASK** *(after step 3)* <br>
You just deleted your whole deployment and brought it back from a file. What did you **not** get back? <br>
**ANSWER** <br>
The **Service**, if you only re-applied the deployment — and therefore the external IP, which will be **different** when you recreate it. More importantly: **anything the Pods had written to their own filesystems is gone.** Pods are disposable; a text file can recreate the *shape* of your application but not its **data**. That's why databases don't live in ordinary Deployments — they need `StatefulSet` and persistent volumes, which is a topic in its own right. Worth knowing the boundary of what you learned today.

**Take-home 1** — a minimal hand-written pair:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: nginx
spec:
  type: LoadBalancer
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80
```

Note the `---` separator: YAML allows multiple documents in one file, so a Deployment and its Service commonly live together.

**Take-home 2** — the broken label match. Change the template label to `app: nginx-typo` while leaving the selector as `app: nginx`, and you get:

```
The Deployment "nginx" is invalid: spec.template.metadata.labels:
Invalid value: map[string]string{"app":"nginx-typo"}:
`selector` does not match template `labels`
```

Kubernetes catches this one at apply time, which is merciful. The **nastier** version is when the **Service's** selector doesn't match — that's **not** validated, the Service simply has no endpoints, and you get a silent failure where everything looks healthy but nothing responds. Diagnose it with `kubectl get endpoints <service-name>`: an empty list means the selector matches nothing.

**Take-home 3** — a readiness probe:

```yaml
      containers:
        - name: hello-world-rest-api
          image: lfacademy/hello-world-rest-api:0.0.2.RELEASE
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /hello-world
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
```

With this in place, Kubernetes won't send traffic to a Pod until that path returns successfully — so a rolling update genuinely waits for the new version to be *serving*, not merely *started*.

**Take-home 8** — ConfigMaps and Secrets. A password baked into an image means: everyone who can pull the image can read it; you need a **rebuild** to rotate it; and the same image can't be used across environments. **ConfigMaps** hold non-sensitive configuration, **Secrets** hold sensitive values, and both are injected into Pods at runtime as environment variables or files. <br>
It's the identical principle to **Jenkins' credentials store** from Session 3 and **`ARM_*` environment variables** in Terraform: **secrets live outside the artifact that uses them.** Worth noting the caveat, though — Kubernetes Secrets are only **base64-encoded**, not encrypted, by default. Real production setups back them with Azure Key Vault.

# Kubernetes & Azure Kubernetes Service — Trainer Script

A full day taking trainees from "I can run a Docker container" to "I can deploy, scale, update and declaratively manage an application on a real Kubernetes cluster". This is written as a script — read it out, adapt where it feels natural, but the intent is that you could deliver this cold from the page.

## Organisation

### Audience

Trainees who have covered **Docker** (building images, running containers, pushing to a registry), **Azure cloud fundamentals**, **bash scripting**, **Jenkins & CI/CD**, and **Terraform**. They can read a config file, use a terminal confidently, and understand what a load balancer does.

They have **no prior Kubernetes**. Every term — pod, node, ReplicaSet, Deployment, Service — is introduced from scratch, and the YAML is explained key by key.

### How this document is laid out — read before delivering

Today you're switching between the **Azure Portal**, the **Cloud Shell**, and (after lunch) a **local terminal**. That's three different places to type things, which is exactly where trainees get lost. Every instruction block is labelled:

- *(Run in Cloud Shell)* — the browser-based terminal inside the Azure Portal
- *(Run from `~/k8s-training/...`)* — a **local** terminal command, in that folder
- *(In the Azure Portal — Kubernetes services)* — a **browser** action, starting from that screen

Navigation is written as breadcrumbs, e.g. **Kubernetes services → your-cluster → Services and ingresses**.

The folders we use today:

| `~/k8s-training` | Parent folder for local work |
| `~/k8s-training/starter-code/kubernetes/01-hello-world-rest-api` | Where the YAML files get generated |

**Every activity has a `**Solution**` block** immediately afterwards.

### 09:00–09:15 — Welcome & Recap: What Docker Didn't Solve

Morning. Let's start by placing today in the story, because Kubernetes makes a lot more sense as *the answer to a specific problem* than as a thing to learn in the abstract.

You already know **Docker**. You can take an application, write a Dockerfile, build an image, and run it anywhere a container runtime exists. In the bash session you wrote a script that built and pushed an image. In the Jenkins session you had a pipeline do it automatically.

*REFER TO RESOURCE 1 - SLIDEE* <br>
![intro-to-kubernetes-1](./resources/intro-to-kubernetes-1.png)

Picture a tech team. You're a developer and you want an application deployed. You go to someone in operations. Because of Docker, all they need to ask is "what's your image?" — then run:

*REFER TO RESOURCE 2 - SLIDEE* <br>
```
docker run -p 8080:8080 lfacademy/hello-world-rest-api:0.0.1.RELEASE
```

One command, and it's running. Operations didn't need to know:
- the language the application was written in
- what frameworks it uses
- what OS it needs
- any other configuration

**ASK** <br>
In the taster day we talked about DevOps breaking down a figurative "wall of confusion" between Dev and Ops. How does that one command demonstrate it? <br>
**ANSWER** <br>
Because the *interface* between the two teams became a single, standard artifact — the image. Dev doesn't have to explain their stack; Ops doesn't have to learn it. All the environment-specific knowledge got packaged into something both sides understand identically. That's the wall coming down in a very literal, practical way.

So Docker standardises **how we package and deploy**, regardless of language, framework or platform. Excellent.

**But then reality arrives.** Once that container is running:
- We want the application to **always** be running — what happens when it crashes at 3am?
- We expect **heavier load** at certain times of year — we want more instances, then fewer
- There are **other applications**, and **new versions** of this one, that also need deploying — without downtime

**ASK** <br>
Could you solve those three things with Docker alone, and a bit of bash? <br>
**ANSWER** <br>
Sort of, badly. You could write a script that polls whether the container is alive and restarts it. You could write another that starts more containers under load. You could write another that swaps versions over. Now you own a homemade, undocumented, untested orchestration system that only you understand — and you still have to run it *somewhere* that itself might fail. This is exactly the kind of problem you don't want to solve yourself.

That's what **Kubernetes** is: a **container orchestration** tool. Docker runs a container; Kubernetes runs *fleets* of containers across *fleets* of machines, and keeps them running.

Today: what Kubernetes is and why, then a real cluster on Azure, then deploying, scaling, self-healing, updating, and finally doing all of it declaratively with YAML files you could put in Git.

**Standing rule, and I mean it today:** we **delete the cluster** before we leave. This is the most expensive thing you've created on this course.

### 09:15–10:00 — Why Kubernetes Exists, and What a Cluster Is

*REFER TO RESOURCE 3 - SLIDEE* <br>
![intro-to-kubernetes-2](./resources/intro-to-kubernetes-2.png)

A **Kubernetes cluster** is a group of servers managed together. Let me show you what having one lets you do — don't type these yet, just watch what each one buys us.

*REFER TO RESOURCE 4 - SLIDEE* <br>
**Deploy an application from an image:**
```
kubectl create deployment hello-world-rest-api --image=lfacademy/hello-world-rest-api:0.0.1.RELEASE
kubectl expose deployment hello-world-rest-api --type=LoadBalancer --port=8080
```

Two commands where Docker took one. Slightly worse so far — but watch.

*REFER TO RESOURCE 5 - SLIDEE* <br>
**Add more instances:**
```
kubectl scale deployment hello-world-rest-api --replicas=3
```

Three instances now, with **load balancing between them handled automatically**. You didn't configure a load balancer. Compare that to the Terraform session, where a load balancer meant a frontend IP, a backend pool, a health probe and a rule.

*REFER TO RESOURCE 6 - SLIDEE* <br>
**Keep them running:**
```
kubectl delete pod hello-world-rest-api-<instance-id>
```

Delete an instance and the application keeps working — and within seconds a replacement appears. You always have three.

*REFER TO RESOURCE 7 - SLIDEE* <br>
**Scale automatically under load:**
```
kubectl autoscale deployment hello-world-rest-api --max=10 --cpu-percent=70
```

Up to 10 instances, automatically, when CPU passes 70%.

**ASK** <br>
Where would automatic scaling like that genuinely matter? <br>
**ANSWER** <br>
Anywhere load is spiky and predictable-ish but not constant — Amazon on Black Friday, a ticketing site the moment Glastonbury goes on sale, a retailer at Christmas. The alternative is provisioning permanently for your worst hour of the year and paying for idle capacity the other 8,759 hours.

*REFER TO RESOURCE 8 - SLIDEE* <br>
**Deploy a new version:**
```
kubectl set image deployment hello-world-rest-api hello-world-rest-api=lfacademy/hello-world-rest-api:0.0.2.RELEASE
```

So out of the box, Kubernetes gives us:
- **Auto-scaling** based on load
- **Automatic load balancing** across available instances
- **Monitoring and self-healing** — an instance dies, another starts
- **Zero-downtime releases**

Imagine an old operations team doing this by hand: someone watching dashboards to restart dead services, someone else adding and removing capacity as traffic moves. Kubernetes lets you manage thousands of microservices with thousands of instances **declaratively** — you state "there should be 100 instances of this service" and Kubernetes makes it so.

**ASK** <br>
That word "declaratively" — where have you met it before on this course? <br>
**ANSWER** <br>
**Terraform.** You describe the desired end state and the tool reconciles reality to match. Kubernetes is the same idea applied to running applications rather than provisioning infrastructure — and it's *continuous*, which is the important difference. Terraform reconciles when you run `apply`; Kubernetes reconciles **constantly**, forever. That's what makes self-healing possible.

#### Kubernetes on the cloud

Kubernetes can run anywhere — locally, in a data centre, on any cloud. Setting it up and managing it yourself is possible but genuinely hard, so most teams use a managed engine:

| Provider | Service | Used by |
|---|---|---|
| **Azure** | **Azure Kubernetes Service (AKS)** | Siemens, HP, Heineken |
| **AWS** | Amazon Elastic Kubernetes Service (EKS) | Netflix, GoDaddy |
| **GCP** | Google Kubernetes Engine (GKE) | YouTube, Google Maps, Google Search |

These provide the underlying configuration and managed servers. We'll use **AKS**.

#### What's actually in a cluster?

Kubernetes is, at heart, a **resource manager**.

**ASK** <br>
What resources does it manage? <br>
**ANSWER** <br>
Servers. Virtual servers in the cloud.

Every provider has a different name for a generic virtual server:
- **Azure**: Virtual Machines
- **AWS**: EC2 instances
- **GCP**: Compute Engine

**Kubernetes calls them `nodes`.**

*REFER TO RESOURCE 9 - SLIDEE* <br>
![intro-to-kubernetes-3](./resources/intro-to-kubernetes-3.png)

Kubernetes can manage thousands of nodes. To oversee that many things it introduces managers — historically called **Master Nodes**, today almost always called the **control plane**.

So a **cluster** is a combination of nodes:
- **Worker nodes** (usually just "nodes") — the ones that actually run your applications
- **Control plane** — oversees the workers: are they available, are they doing work, is the desired state being met

**NOTE FOR TRAINERS** <br>
Worth calling out directly, because it's a genuine AKS advantage: Azure **fully manages and hosts the control plane at no extra cost**. You don't see it, configure it, or pay for it as a resource — you only see and pay for the **worker nodes** in your **node pool**. That differs from providers where you choose a zonal versus regional control plane or pay a per-cluster management fee. With AKS there is simply nothing to configure there. <br>
**END OF NOTE**

**ASK** <br>
Given you just described a control plane that constantly checks whether reality matches the desired state — what does that remind you of from the Terraform sessions? <br>
**ANSWER** <br>
The three states. The control plane holds the **desired state** ("3 replicas of this image"), observes the **actual state** ("only 2 pods running"), and continuously reconciles. The difference is that Terraform does it when *you* run a command; the Kubernetes control plane does it in a permanent loop. It's genuinely called the **reconciliation loop**, and it's the single most important idea in Kubernetes.

#### While it's building — a few facts

- You'll see Kubernetes abbreviated **K8s** — `K`, then *eight letters*, then `s`. (The same pattern gives you `i18n` for internationalisation and `a11y` for accessibility.)
- The logo is a ship's helm — the name comes from the Greek for *helmsman* or *pilot*. The whole vocabulary is nautical: containers, pods, helm charts. It's all one extended metaphor about steering cargo.
- The managed offerings again: **AKS** (Azure), **EKS** (AWS), **GKE** (GCP)

#### Touring the cluster

Once it's ready:

*(In the Azure Portal — Kubernetes services → your cluster)*

On the top-level list you can see the cluster's **name**, **location**, **Kubernetes version** and **number of nodes**.

Click into the cluster. On the left-hand panel you'll find the tools we'll use all day:
- **Node pools** — where your worker nodes live
- **Workloads** — the applications running in the cluster
- **Secrets** — secure storage for values tied to the cluster
- **Services and ingresses** — how traffic reaches your applications

**Overview** shows:
- **Kubernetes version** — which version is running
- **API server address** — how tools like `kubectl` reach the control plane
- **Region** — where your nodes live

**NOTE FOR TRAINERS** <br>
Unlike GKE, which shows a "control plane zone" alongside "default node zones", AKS **doesn't expose control-plane location at all**. That's Azure's infrastructure to manage, not ours to inspect. Everything visible and configurable relates to **nodes**. <br>
**END OF NOTE**

*(In the Azure Portal — your cluster → Node pools)*

Click into the node pool, then into an individual node. You'll see:

- **CPU requested** — measured in **mCPU**, "milliCPU". `1000 mCPU` is one whole CPU core, so `250 mCPU` is a quarter of a core. This is a **Kubernetes-level** unit, identical on every cloud
- **CPU allocatable** — how much is available for your applications
- **Memory available** — likewise

**ASK** <br>
You chose a VM size with, say, 2 vCPUs and 4GB of memory. Look at what's actually allocatable — it's less. Where did the rest go? <br>
**ANSWER** <br>
Kubernetes itself. Every node runs agent processes — the kubelet, the container runtime, networking components — and the operating system needs headroom too. That overhead is reserved before your applications get anything. It's a real planning consideration: a cluster of many tiny nodes wastes proportionally far more on overhead than a cluster of fewer larger ones.

**HANDS ON (remaining time)** <br>
1. *(In the Azure Portal)* Create an AKS cluster using the **Standard** preset, in a new resource group, in **UK South**.
2. While it provisions, explore the Kubernetes services landing page and note where **Node pools**, **Workloads** and **Services and ingresses** live.
3. Once ready, click into the cluster and note the **Kubernetes version** and **API server address**.
4. Go into **Node pools** and find the **VM size**, then click into a node and find its **CPU allocatable** and available memory.
5. Compare the node's advertised VM size against what's actually allocatable, and work out roughly what percentage Kubernetes reserved.
**END OF NOTE**

**Solution**

There's no code for this one — it's Portal navigation — but the answers students should arrive at:

**Step 3** — the Kubernetes version will be whatever AKS currently defaults to (e.g. `1.30.x`). The API server address is a hostname ending `.azmk8s.io`. That hostname is what `kubectl` talks to.

**Step 4** — the default node pool VM size is typically `Standard_DS2_v2` (2 vCPU, 7 GiB) or similar, depending on the current AKS default.

**Step 5** — expect roughly **10–25%** of CPU and memory to be reserved, with proportionally more reserved on smaller nodes. The exact reservation follows a published sliding scale. The takeaway: **you never get 100% of what you pay for**, and small nodes are inefficient.

If a student's cluster fails to create, the usual causes are **insufficient quota** for the VM family in that region (try a different region or a smaller VM size), or **insufficient credit**.

Azure gives us a browser-based terminal, so nothing needs installing yet.

*(In the Azure Portal — top-right toolbar)*
- Click the **`>_`** icon — hovering says **Cloud Shell**

![intro-to-kubernetes-8](./resources/intro-to-kubernetes-8.png)

It takes a moment to start, and the first time it'll ask to create a small **storage account** to persist your files between sessions. Let it — that's normal, and it's the same prompt you saw in the PowerShell section of the bash session.

It opens as a pane at the bottom of the screen; there's a maximise option that makes it far more comfortable to work in.

#### Connecting to the cluster

*(In the Azure Portal — your cluster → Overview)*
- Click **Connect**

![intro-to-kubernetes-9](./resources/intro-to-kubernetes-9.png)

Copy the command shown under **Azure CLI**:

*(Run in Cloud Shell)*
```bash
az aks get-credentials --resource-group rg-aks-emilesherrott-devops --name emilesherrott-cluster
```

Reading it:
- `az aks get-credentials` — fetch the credentials needed to talk to a cluster
- `--name` — which cluster
- `--resource-group` — which resource group it lives in

What this actually does is write connection details into a **kubeconfig** file (`~/.kube/config`), which is what `kubectl` reads to know *which cluster to talk to and how to authenticate*. If you manage several clusters, they all live in that one file and you switch between them — the file is called a "context" per cluster.

If prompted to authenticate, approve it. Re-run the command if anything went wrong.

#### kubectl

**`kubectl`** — pronounced "cube-cuttle" or "cube-control" — is the Kubernetes controller CLI. It's the tool for interacting with clusters, and it's excellent for one specific reason: **it doesn't care what's underneath**. The same commands work against a cluster on your laptop, in a data centre, on AKS, EKS or GKE. You learn it once.

*(Run in Cloud Shell)*
```bash
kubectl version
```

![intro-to-kubernetes-10](./resources/intro-to-kubernetes-10.png)

Two versions come back:
- **Client Version** — the `kubectl` binary you're running
- **Server Version** — the Kubernetes version of the cluster you're connected to

Seeing a Server Version at all confirms you're connected.

#### Deploying the application

*(Run in Cloud Shell)*
```bash
kubectl create deployment hello-world-rest-api --image=lfacademy/hello-world-rest-api:0.0.1.RELEASE
```

Breaking that down:
- `kubectl create deployment` — make a Deployment (we'll unpack what that means shortly)
- `hello-world-rest-api` — the name we're giving it
- `--image=...` — which container image to run

**Where does that image come from?**

*REFER TO RESOURCE 10 - SLIDEE* <br>
![intro-to-kubernetes-11](./resources/intro-to-kubernetes-11.png)

The journey you already know from the Docker session:
1. Application code
2. A Dockerfile builds it into an **image**
3. The image is **pushed** to a registry — here, Docker Hub

When you run that command, Kubernetes finds and **pulls** the image from Docker Hub onto a node.

*REFER TO RESOURCE 11 - SLIDEE* <br>
**NOTE FOR STUDENTS** <br>
If you build your own images on an Apple Silicon Mac, they default to the **`linux/arm64/v8`** platform — fine locally, but AKS nodes typically run **`linux/amd64`**. An arm64 image on an amd64 node fails with a confusing `exec format error`. Build for the cloud explicitly: <br>
`docker build --platform linux/amd64 -t lfacademy/hello-world-rest-api:0.0.1.RELEASE .` <br>
"Platform" here just means the OS and CPU architecture. AKS *does* support ARM-based node pools if you specifically want to match ARM images — we're not using that today. <br>

### 12:15–13:00 — Pods and ReplicaSets
*(Exercise + Challenge)*

Getting an application running was the easy part. Understanding what happened behind the scenes is where the real learning is — and there are several new concepts.

*(Run in Cloud Shell)*
```bash
kubectl get events
```

A lot of events come back, all relating to what the cluster has been doing.

![intro-to-kubernetes-14](./resources/intro-to-kubernetes-14.png)

You can see a **pod** created, an image pulled, and a sequence of steps starting a container. There's also a **replica set** and a **deployment**.

![intro-to-kubernetes-15](./resources/intro-to-kubernetes-15.png)

And a **service**.

We created *one deployment* and *exposed it*. Kubernetes made a Pod, a ReplicaSet, a Deployment and a Service. Why four things?

#### The Single Responsibility Principle

Kubernetes deliberately follows the **Single Responsibility Principle**: **one concept, one responsibility.** Rather than one big "running application" object, it splits the job:

| Object | Its one job |
|---|---|
| **Pod** | Run containers |
| **ReplicaSet** | Ensure a specific number of Pods exist |
| **Deployment** | Manage releases and version changes without downtime |
| **Service** | Provide a stable network endpoint |

`kubectl create deployment` made the **Pod, ReplicaSet and Deployment**. `kubectl expose deployment` made the **Service**.

**ASK** <br>
Why split it up? Why not have one object that does all four jobs? <br>
**ANSWER** <br>
Because the four jobs change independently and at different rates. You change how many instances you want far more often than you change which version is deployed. You change the version far more often than you change the network endpoint — and you specifically *don't want* the endpoint to change when the others do. Separating them means each can be reasoned about, changed and replaced without touching the others. It's exactly the argument for splitting a monolith into modules, applied to the runtime.

#### Pods

*REFER TO RESOURCE 13 - SLIDEE* <br>
![intro-to-kubernetes-21](./resources/intro-to-kubernetes-21.png)

A **Pod** is the **smallest deployable unit** in Kubernetes. You cannot create a bare container — every container lives inside a Pod.

*(Run in Cloud Shell)*

![intro-to-kubernetes-22](./resources/intro-to-kubernetes-22.png)

- **READY** — showing `1/1`: how many containers in the Pod are ready, out of how many exist

**A Pod can hold multiple containers.** They share the Pod's resources, share its IP, and can talk to each other over **`localhost`**.

**ASK** <br>
When would you deliberately put two containers in one Pod, rather than two separate Pods? <br>
**ANSWER** <br>
When they're genuinely inseparable — one is a helper for the other and they must live and die together on the same machine. The classic example is a **sidecar**: your application container plus a log-shipping container that reads the app's log files, or a proxy that handles TLS. If they could sensibly run on different machines, or scale independently, they belong in separate Pods. The test is: "would it ever make sense to have three of one and five of the other?" If yes, separate Pods.

The description says a Pod is a collection of containers that can run on a **host**, created by clients and scheduled onto hosts.

"Host" here means a **node** — one of our cluster's servers. So:

**A node can hold many Pods. A Pod can hold many containers.**

`describe` gives you far more than `get`. Notable fields:

- **Name** and **IP**
- **Node** — which server it's running on
- **Namespace** — set to `default`. **Namespaces provide isolation within a cluster.** You could run Dev and QA in the same cluster and separate their resources by namespace
- **Labels** — here `app=hello-world-rest-api`. **This is how Pods, ReplicaSets and Services find each other** — via labels and *selectors* rather than by name or IP
- **Annotations** — metadata: author, build ID, and so on

**ASK** <br>
Labels are just arbitrary key/value strings. Why is that a better way to connect a Service to its Pods than listing Pod names or IPs? <br>
**ANSWER** <br>
Because Pods are disposable — names and IPs change constantly. A Service that said "send traffic to Pod `m8jh4`" would break the moment that Pod was replaced. Instead it says "send traffic to anything labelled `app=hello-world-rest-api`", and whatever currently matches gets the traffic. It's a *query*, evaluated continuously, not a fixed list. That's what makes the whole thing survive Pods coming and going.

### 14:00–14:45 — Deployments and Zero-Downtime Releases
*(Talk + demo)*

We've covered Pods and ReplicaSets. So why do we need a **Deployment** on top?

Picture version 1 of an application running, and you want version 2 live. The requirement is **zero downtime** — users keep using the app throughout the transition.

#### Deliberately breaking it first

- `DUMMY_IMAGE:test` — an image path that doesn't exist

**Two ReplicaSets now:**

![intro-to-kubernetes-36](./resources/intro-to-kubernetes-36.png)

The sequence in the events:
- A new **Deployment** rollout started
- The Deployment created a new **ReplicaSet**
- That ReplicaSet asked for **one** Pod
- The Pod **failed to start**
- ...and everything stopped there

*REFER TO RESOURCE 12 - SLIDEE* <br>
![intro-to-kubernetes-37](./resources/intro-to-kubernetes-37.png)

**ASK** <br>
This is the single most valuable thing in today's session. Why did a completely broken deployment cause **zero** user impact? <br>
**ANSWER** <br>
Because the Deployment creates the new version **alongside** the old one and only scales the old one down as the new one proves healthy. The new Pod never became Ready, so the old ReplicaSet was never scaled down — all three original Pods kept serving. The rollout simply stalled. Compare that to the Terraform session: an `apply` that fails halfway leaves you in a broken half-applied state with no automatic rollback. A Kubernetes Deployment refuses to take down working capacity for something that isn't working yet.

This is exactly the same instinct as the Jenkins pipeline gate — **don't let the broken thing reach users** — enforced automatically at runtime.

*(Run in Cloud Shell)*

**END OF NOTE**

*(Run in Cloud Shell)*
```bash
kubectl get rs
```

![intro-to-kubernetes-39](./resources/intro-to-kubernetes-39.png)

**Three ReplicaSets:**
1. The original v1 — now scaled to 0
2. The broken DUMMY one — 0
3. The new v2 — 3 Pods running

*(In your browser)* — refresh. You're on **v2**.

*(Run in Cloud Shell)*
```bash
kubectl get events --sort-by=.metadata.creationTimestamp
```

The rollout sequence, step by step:
- Deployment creates a new ReplicaSet for **v2**
- Gives it **one** Pod
- That Pod runs a v2 container and becomes Ready
- Scales **v1 down** to 2
- Scales **v2 up** to 2
- Scales **v1 down** to 1
- Scales **v2 up** to 3
- Scales **v1 down** to 0

**It updates one Pod at a time**, always keeping enough healthy capacity serving. That's a **rolling update**, and it's the default strategy.

**ASK** <br>
Those old ReplicaSets are still sitting there at 0 replicas. Why keep them rather than delete them? <br>
**ANSWER** <br>
**Rollback.** The old ReplicaSet still knows exactly which image and configuration it ran. If v2 turns out to be broken in a way that only shows up under real traffic, `kubectl rollout undo deployment hello-world-rest-api` scales the previous ReplicaSet back up and the current one down — in seconds, with no rebuild and no pipeline run. Keeping the history is what makes instant rollback possible. (`revisionHistoryLimit` controls how many are retained; you'll see it in the YAML later.)

Worth showing them:

*(Run in Cloud Shell)*
```bash

kubectl rollout status deployment hello-world-rest-api
```

#### Summary of the four concepts

*REFER TO RESOURCE 13 - SLIDEE* <br>
![intro-to-kubernetes-40](./resources/intro-to-kubernetes-40.png)

**Pods** — wrappers for a set of containers. Have an IP address, labels and annotations.

**ReplicaSets** — ensure a specific number of Pods run. In practice each is tied to **one release version**.

**Deployments** — manage release upgrades without downtime. Strategies include:
- **Rolling update** (the default) — replace Pods gradually, as we just saw
- **Blue/green** — stand up the full new version, then switch traffic across at once
- **Canary** — send a small percentage of traffic to the new version first

Kubernetes has real depth beyond this, but these four concepts carry most of the day-to-day work, and they're why it's used on every major cloud by enterprises everywhere: reliable technology, quick deployment, low effort.

### 14:45–15:00 — Services, Regions and Availability Zones

#### Why Services exist

*(Run in Cloud Shell)*
```bash
kubectl get pods -o wide
```

![intro-to-kubernetes-41](./resources/intro-to-kubernetes-41.png)

**NOTE FOR TRAINER**: *DON'T CLEAR THE TERMINAL* — you want the old IPs visible for comparison.

Each Pod has its own IP. But the endpoint you've been visiting in the browser matches **none of them** — traffic is being distributed across all three.

Now delete a Pod:

*(Run in Cloud Shell)*
```bash
kubectl delete pod <pod-name>
# wait a moment
kubectl get pods -o wide
```

**ASK** <br>
Compare against the earlier output. What's different? <br>
**ANSWER** <br>
The replacement Pod has a **new IP address**. Every Pod gets a fresh IP when it starts.

That's a problem. If users connected directly to Pod IPs, every self-heal, every scale event and every release would break their connection. **We need one endpoint that never changes.**

**As far as Kubernetes is concerned, a Pod is a throwaway resource.** They're built expecting to be destroyed and recreated. The job of a **Service** is to provide an **always-available interface** to whatever Pods currently exist — a permanent address in front of impermanent things.

To recap what created what:
- `kubectl create deployment <name> --image=<image>` → Pods, ReplicaSet, Deployment
- `kubectl expose deployment <name> --type=<type> --port=<port>` → Service

*(In the Azure Portal — your cluster → Services and ingresses → your service)*

![intro-to-kubernetes-42](./resources/intro-to-kubernetes-42.png)

You can see the labels, the associated deployment, the external IP, and the Pods currently serving requests.

*(In the Azure Portal — search **Load balancers**)*

![intro-to-kubernetes-43](./resources/intro-to-kubernetes-43.png)

There's a real **Azure Standard Load Balancer**, created automatically for the Service, in the same resource group as your node pool.
- **Frontend IP configuration** — the IP you've been using
- **Backend pools** — your nodes, and through them your Pods

**ASK** <br>
In the Terraform session you built a load balancer by hand: a public IP, the LB, a backend pool, a health probe and a rule. Here, one `kubectl expose` did all of it. Is that strictly better? <br>
**ANSWER** <br>
It's faster and far less error-prone for the common case — but you've given up fine-grained control, and it's now *implicit*: nothing in your Git repository says "there is an Azure load balancer". Someone reading the Terraform knows exactly what exists; someone reading a `kubectl expose` command has to know that Kubernetes provisions cloud resources on their behalf. That's the trade every abstraction makes. It also means **deleting the Service is what deletes the load balancer** — you can't manage it in the Portal.

#### Service types

*(Run in Cloud Shell)*
```bash
kubectl get services
```

![intro-to-kubernetes-44](./resources/intro-to-kubernetes-44.png)

Two services: our **LoadBalancer**, and **`kubernetes`**, which is a **ClusterIP**.

- **ClusterIP** — reachable **only from inside the cluster**. Note it has **no EXTERNAL-IP**. Used for internal service-to-service communication — e.g. your API talking to a database
- **LoadBalancer** — asks the cloud provider for a public load balancer and external IP. What we used
- **NodePort** — opens a specific port on every node; reachable from outside via any node's IP. A middle ground, more common outside managed clouds

#### Regions and availability zones

We chose a region when creating the cluster. Worth a moment on why.

*(In your browser)* — search **Azure global infrastructure**:
https://azure.microsoft.com/en-us/explore/global-infrastructure/geographies/

Azure runs datacentres across **60+ regions** — more than any other major cloud provider — grouped into **geographies** to help meet data-residency requirements. The map shows them clustered in populated, developed parts of the world.

**ASK** <br>
What is **latency**? <br>
**ANSWER** <br>
The time it takes for requests and responses to traverse a network.

If all your users are in Wolverhampton but you deploy to **Australia Southeast** (Melbourne), every request makes a round trip across the world. That's why you put clusters near your users.

**ASK** <br>
What do we mean by **availability**? <br>
**ANSWER** <br>
The ability to access resources. If there were flooding in London, users shouldn't lose the application entirely.

So we **distribute** across regions — if something happens in **UK South**, we can serve from **France Central** with still-reasonable performance. There are also **legal** reasons: some countries require citizens' data to stay within their borders.

Within a region there are **Availability Zones** — physically isolated locations with independent power and networking. Azure uses the same term as AWS (GCP just says "zones"). Most Azure regions that support AZs have **3**.

**NOTE FOR TRAINERS** <br>
One difference worth flagging versus GCP: **not every Azure region supports Availability Zones at all.** GCP regions uniformly have zones; Azure's don't. Always check the [regions page](https://azure.microsoft.com/en-us/explore/global-infrastructure/geographies/) for whichever region you're planning to use — this catches people out when designing for resilience. <br>
**END OF NOTE**

If one area of London loses power, the hope is other zones are unaffected — so a zone failure doesn't take out the region for you.

`>` writes (and overwrites) — exactly as it did with `ls -la > listing.txt`.

Open `deployment.yaml`. Rather than trying to understand every line, know the **four top-level keys** every Kubernetes YAML file has:

| Key | Meaning |
|---|---|
| `apiVersion` | Which version of the Kubernetes API this object uses (e.g. `apps/v1`) |
| `kind` | What type of object this is — `Deployment`, `Service`, `Pod` |
| `metadata` | Name, namespace, labels, annotations — how it's identified |
| `spec` | **The desired state.** This is the part you write and change |

There's a fifth, `status`, which Kubernetes fills in — the **actual state**. You never write it.

**ASK** <br>
`spec` is desired state and `status` is actual state, maintained by the cluster. What does that map onto from the Terraform sessions? <br>
**ANSWER** <br>
`spec` is the **Desired State** — your `.tf` files. `status` is the **Actual State**. And the control plane's reconciliation loop is doing continuously what `terraform apply` does on demand. Once you see that the same three-state model underlies both tools, Kubernetes YAML stops being mysterious.

Find these in the files:
- **deployment.yaml → `spec.replicas`** — the number of Pods
- **deployment.yaml → `spec.template.spec.containers[].image`** — the image being run
- **deployment.yaml → `status.availableReplicas`** and `updatedReplicas` — currently 3
- **service.yaml → `spec.type`** — `LoadBalancer`

Note `spec.template` — that's a **Pod template**. The Deployment's spec *contains a description of the Pods to create*. That nesting is the Deployment → ReplicaSet → Pod hierarchy, expressed in one file.

#### Part A3 (≈15 min) — Apply a change from YAML

Let's change the replica count declaratively rather than with `kubectl scale`.

**deployment.yaml**
```yaml
spec:
  progressDeadlineSeconds: 600
  # UPDATED YAML
  replicas: 2
  revisionHistoryLimit: 10
  selector:
    matchLabels:
      app: hello-world-rest-api
```

Save, then:

*(Run from `~/k8s-training/starter-code/kubernetes/01-hello-world-rest-api`)*
```bash
kubectl apply -f deployment.yaml
kubectl get pods
```

![intro-to-kubernetes-58](./resources/intro-to-kubernetes-58.png)

Two Pods.

**`kubectl apply -f <file>`** is the declarative command:
- `apply` — "make reality match this file". Creates what's missing, updates what differs, leaves what matches alone
- `-f` — the file to read

**ASK** <br>
What's the practical difference between `kubectl apply -f deployment.yaml` and `kubectl scale deployment ... --replicas=2`? <br>
**ANSWER** <br>
The end state is identical — but only one of them leaves a **record**. The YAML file can be committed, diffed, reviewed in a pull request, and re-applied to a different cluster to produce the same result. The `scale` command exists only in your shell history. And `apply` is **idempotent**: run it ten times and nothing changes after the first. That word should be familiar from the automation session — it's the same property that makes it safe to run in a pipeline.

**NOTE FOR TRAINER** <br>
You'll hit errors applying further changes without cleaning up the generated file. `kubectl get -o yaml` dumps **everything**, including runtime-only fields (`status`, `metadata.uid`, `resourceVersion`, `creationTimestamp`, `managedFields`) that Kubernetes rejects or ignores on apply. That's the point of the next part — don't skip it, and warn students before they start experimenting. <br>
**END OF NOTE**

#### Part B (≈40 min) — Clean the YAML into something you'd commit

Generated YAML is a **starting point**, not a finished artifact. A file you'd actually put in Git contains only what *you* are asserting, not what the cluster reported back.

**Your task:** produce a `deployment.yaml` and a `service.yaml` that are:
- Free of runtime-generated fields
- Applicable repeatedly with no errors
- Readable — someone could review them in a pull request and understand what they do

**Delete from both files:**
- The entire `status:` block at the bottom
- Inside `metadata`: `uid`, `resourceVersion`, `generation`, `creationTimestamp`, `selfLink`, `managedFields`, and the `annotations` block containing `deployment.kubernetes.io/revision` and `kubectl.kubernetes.io/last-applied-configuration`
- In `service.yaml`: `spec.clusterIP`, `spec.clusterIPs`, and anything under `status.loadBalancer`

**Then test properly:**

*(Run from `~/k8s-training/starter-code/kubernetes/01-hello-world-rest-api`)*
```bash
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f deployment.yaml    # run it AGAIN — should be clean, "unchanged"
```

**Then prove they're real infrastructure-as-code:**
1. Change `replicas` to `4` in the file, apply, and confirm with `kubectl get pods`
2. Change the image tag in the file to `0.0.1.RELEASE`, apply, and watch the rolling update with `kubectl get pods -w`
3. Delete the deployment entirely (`kubectl delete deployment hello-world-rest-api`), then recreate it **from your file alone**

**Solution**

A cleaned `deployment.yaml` — everything below is something you're *asserting*, nothing is reported state:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-world-rest-api
  labels:
    app: hello-world-rest-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hello-world-rest-api
  template:
    metadata:
      labels:
        app: hello-world-rest-api
    spec:
      containers:
        - name: hello-world-rest-api
          image: lfacademy/hello-world-rest-api:0.0.2.RELEASE
          ports:
            - containerPort: 8080
```

A cleaned `service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: hello-world-rest-api
  labels:
    app: hello-world-rest-api
spec:
  type: LoadBalancer
  selector:
    app: hello-world-rest-api
  ports:
    - port: 8080
      targetPort: 8080
      protocol: TCP
```

Reading the important parts:

- **`spec.selector.matchLabels`** (Deployment) — "the Pods I manage are the ones with this label"
- **`spec.template.metadata.labels`** — "the Pods I create get this label". **These two must match**, or the Deployment creates Pods it doesn't consider its own. It's the most common YAML mistake there is
- **`spec.selector`** (Service) — "send traffic to Pods with this label". Same label again — that's the whole link between Service and Pods
- **`port` vs `targetPort`** — `port` is what the Service listens on; `targetPort` is the port on the container. They're often the same and don't have to be

The full test sequence:

*(Run from `~/k8s-training/starter-code/kubernetes/01-hello-world-rest-api`)*
```bash
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml

# Idempotency — the second run should report "unchanged"
kubectl apply -f deployment.yaml

# 1. Scale declaratively: edit replicas to 4, then
kubectl apply -f deployment.yaml
kubectl get pods

# 2. Roll back a version: edit image tag to 0.0.1.RELEASE, then
kubectl apply -f deployment.yaml
kubectl get pods -w              # watch the rolling update live, Ctrl+C to stop
kubectl get rs -o wide           # see the ReplicaSets swap over

# 3. Delete and recreate from the file alone
kubectl delete deployment hello-world-rest-api
kubectl get pods                 # all gone
kubectl apply -f deployment.yaml
kubectl get pods                 # back, from the file
```

**The point of step 3** — this is the payoff of the whole day. Your entire application definition is now **a text file**. Delete everything, apply the file, and it comes back identically. That file can be reviewed in a pull request, applied to a different cluster, or run by a Jenkins pipeline. It is Infrastructure as Code, one layer above Terraform: Terraform provisions the cluster, this deploys onto it.

**Stretch, if anyone finishes early:**

```bash
# Combine both files into one apply
kubectl apply -f .

# Preview a change without making it — the kubectl equivalent of 'terraform plan'
kubectl diff -f deployment.yaml

# Validate without applying
kubectl apply -f deployment.yaml --dry-run=client
```

`kubectl diff` is genuinely underused and worth showing — it prints exactly what would change, which is precisely the review step that makes declarative config safe.

**Solution** *(for the guided ones — 1, 3, 4)*

**Take-home 1** — a minimal, hand-written pair:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: nginx
spec:
  type: LoadBalancer
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80
```

Note the `---` separator: YAML allows multiple documents in one file, so a Deployment and its Service commonly live together.

**Take-home 3** — `kubectl rollout undo deployment <name>` scales the **previous** ReplicaSet back up to the desired replica count and scales the **current** one down to zero. It doesn't rebuild or re-pull anything — the old ReplicaSet still holds the full Pod template, so rollback is just a scaling operation and takes seconds. That's why those zero-replica ReplicaSets are worth keeping around.

**Take-home 4** — a **readiness probe** tells Kubernetes whether a Pod is ready to *receive traffic*; a **liveness probe** tells it whether the Pod is still alive or needs restarting. Without a readiness probe, Kubernetes considers a Pod ready as soon as the container process starts — which for most applications is *before* it can actually serve requests. During a rolling update that means it would scale down the old version while the new one is still warming up, causing exactly the downtime the Deployment is meant to prevent. It's the same job as the `azurerm_lb_probe` you configured in Terraform, but evaluated continuously by the cluster rather than by a cloud load balancer.
